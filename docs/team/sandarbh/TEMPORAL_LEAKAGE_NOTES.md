## Core Principle

At prediction date **T**, only information actually available at or before **T** may be
used as model input.

Any feature that implicitly or explicitly contains information from after T is
a **temporal leak** and will cause optimistically biased model performance that
does not replicate in production.

---

## Why This Is Difficult for Infrastructure Data

Monthly Flash Reports are **retrospective** â€” they report the state of a project as
of a past cut-off date.

However, the state itself (revised cost, revised completion date) was generated by
an administrative process that may have occurred weeks or months before the report.

This means:

1. The "observation date" and the "event date" may differ.
2. A revision recorded in the July report may have been approved in May.
3. Future models must carefully track which date is used for each feature.

## Known Leakage Risks

### LR-01 â€” Using Revised Cost to Predict Cost Overrun

| Attribute | Value |
|---|---|
| Risk | HIGH |
| Description | If predicting whether a cost overrun will occur, using the future revised cost as a feature is a direct leak. |
| Resolution | Features must be derived from observations at or before prediction date T. |
| Status | To be enforced at Gate 3. |

### LR-02 â€” Using Revised DOC to Predict Schedule Overrun

| Attribute | Value |
|---|---|
| Risk | HIGH |
| Description | Same as LR-01 but for schedule. |
| Resolution | As above. |
| Status | To be enforced at Gate 3. |

### LR-03 â€” Using Actual Completion Date to Predict Completion

| Attribute | Value |
|---|---|
| Risk | CRITICAL |
| Description | Actual completion date is only known after the project completes. Using it as a feature for a model predicting mid-project outcomes is direct leakage. |
| Resolution | `actual_completion_date` is an **outcome label**, not a feature. |
| Status | To be enforced at Gate 3. |

### LR-04 â€” Random Train/Test Split of Project-Month Rows

| Attribute | Value |
|---|---|
| Risk | HIGH |
| Description | Randomly splitting individual month rows across train/test means the model may train on month T+6 of a project and test on month T of the same project. This is a temporal leak. |
| Resolution | Splits must be done at the project level or at a temporal cut-off date. |
| Status | To be enforced at Gate 3. |

### LR-05 â€” Using Physical Progress to Predict Near-Term Cost Revision

| Attribute | Value |
|---|---|
| Risk | MEDIUM |
| Description | Physical progress at time T is available and is legitimate. However, if the feature is engineered as a future change (e.g., progress delta between T and T+3), that is a leak. |
| Resolution | Feature engineering must be carefully time-indexed. |
| Status | To be tracked during feature engineering. |

### LR-06 â€” Cumulative Expenditure Trends

| Attribute | Value |
|---|---|
| Risk | MEDIUM |
| Description | Cumulative expenditure at T is legitimate. Future cumulative expenditure is a leak. Spending velocity must be computed from past observations only. |

## Architectural Implication for the Dataset

Every row in `project_month.csv` must include `reporting_month` so that any
future model can filter: "use only observations where `reporting_month <= prediction_date`".

The `source_file` and `source_page` fields exist partly to allow this temporal audit.

---

## What a Valid Prediction Horizon Looks Like

Example: Predicting cost overrun **6 months in advance**

```
At reporting_month = 2025-01:
  - Features: all fields from project_month WHERE reporting_month <= 2025-01
  - Label: did revised_cost INCREASE between 2025-01 and 2025-07?
```

The label is derived from FUTURE observations, but it is computed as a **label
during dataset preparation** â€” it is NOT passed to the model as a feature.

This is the correct approach. It is documented here to prevent confusion during Gate 3.
